# P1 RAG MVP: マニュアル検索+出典付き回答

**元資料**: `docs/design-v5-hybrid.md` §8(P1)、§3.1・§3.4・§3.6・§4 / `docs/env-setup-record.md` §2・§7
**用語**: 分からない用語は `docs/glossary.md` を参照

## ゴール

マニュアルの質問に、出典付きで回答できる(F-01, F-02, F-06の実証)。

## 対応する必須要件

| ID | 要件 |
|---|---|
| F-01 | 回答の根拠はマニュアルのみ。LLMの学習知識・Web検索による回答を禁止 |
| F-02 | 回答時に出典を提示(ファイル名必須、見出しが取得できる場合はあわせて提示) |
| F-06 | マニュアル更新の自動反映(R2に置くだけで索引化 — AI Searchのマネージド機能で実現) |

## スコープ

1. **非同期処理の骨格完成**: webhook Lambda → SQS(+DLQ)→ worker Lambda(P0で未構築の場合)
   - 冪等性確保: `webhookEventId` をDynamoDBに条件付き書き込み、既存ならスキップ(§3.3)
2. **worker Lambda → Cloudflare AI Search 連携**
   - エンドポイント: `https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/autorag/rags/line-manual-bot/search`
     - 製品名は「AI Search」だが**検索系APIのパスは旧名の`autorag/rags`のまま**。`ai-search/instances/{NAME}/search` は存在せず401になる(2026-09-06実測 — env-setup-record §7-1)
   - **リクエストは `{"query": "質問文"}`**(`messages`配列を送ると400。当初specの記載は誤りだった)
   - 回答文まで生成する `.../ai-search` エンドポイントは**使わない**。生成はClaude Haiku側で行い、F-01とP2のJSON自己判定を自前で担保する
   - トークン: SSM `/line-manual-bot/cloudflare/ai-search-token`(AI Search: 編集権限)
3. **Claude Haiku 4.5 での回答生成**
   - プロンプトには検索ヒットチャンクのみを入れる。ツールは一切与えない(F-01の物理的担保、§3.4 第0段)
   - APIキー: SSM `/line-manual-bot/anthropic/api-key`
   - LLMに生成させるのは**回答本文のみ**。出典はLLMに出力させない(下記4)
4. **出典表示(F-02)のフォールバック実装**(§3.4)
   - 出典は**コード側**で検索結果(ファイル名+チャンク本文)から組み立てる
   - チャンク本文の先頭付近にMarkdown見出し(`#`〜`###`)があれば「ファイル名 > 見出し」で提示
   - 見出しが取れなければファイル名のみ提示
5. **マニュアル(.md)のR2アップロードと索引化確認**
   - 置き場所は R2バケット `line-manual-bot-manuals` の **`manuals/`(複数形)** 配下。AI Searchの対象パス指定が `manuals/*` のため、`manual/` など1文字でも違うと同期ジョブが `0 files seen` になり、エラーも警告も出ないまま検索が常に0件になる(2026-09-06に実際に踏んだ)

## 実測タスク(P1の重要な目的)

- [x] **AI Search呼び出しのレイテンシを実測する**(2026-09-06、マニュアル1件・5クエリ)
  - 630ms / 4,253ms / 4,679ms / 5,778ms / 8,708ms(中央 4,679ms、**最大 8,708ms**)
  - **要判断**: 検索タイムアウトは現在10秒で、最大値との余裕が1.3秒しかない。→ 下記「積み残し」参照
- [x] **日本語検索精度を実測する**(2026-09-06)
  - マニュアルに載っている質問4件すべてで、**正しいセクションが1位**(ダイヤチップ→「2 部品の交換頻度と交換方法」/ ろ過フィルター→「2-1-7 ろ過フィルター」/ 水の逆流→「3-8 水が逆流する」/ AT-5の特長→「1-3 ほーるマンAT-5の特長」)
  - マニュアルに無い質問(「有給休暇の申請方法は?」)は**ヒット0件**。誤ヒットしない
  - 関連ヒットのスコアは 0.52〜0.62、同一ファイル内の関連薄いチャンクは 0.41〜0.47(P2のθ1の参考値)
  - **結論: §4の逃げ道(ハイブリッド検索の有効化・埋め込みモデルの差し替え)は現時点で不要**
- [x] **見出しメタデータの取得可否を確認し、F-02フォールバックの要否を確定する**(2026-09-06)
  - レスポンスの `attributes` に**見出しは含まれない**(入っているのは `timestamp` / `folder` / 空の `filename` / `file` のみ)
  - **したがって本文から見出しを抽出するフォールバックは必須**。実測した4件すべてで正しい見出しを抽出できている
  - Markdown原本のため `#`記法が確実に存在することが、この抽出の前提を支えている

### 実測で判明したレスポンス構造(重要)

`result.data[]` は**チャンク単位ではなくファイル単位**で、1要素の中の `content[]` に**複数のチャンク**が入る。

```
result.data[0] = {
  file_id, filename: "manuals/xxx.md", score: 0.596,   ← ファイルレベル(= content内の最高スコア)
  attributes: {...},
  content: [ {id, type, text, score: 0.596}, {…, score: 0.474}, {…, score: 0.442}, {…, score: 0.432} ]
}
```

実測では1質問あたり `content` が1〜6件、結合すると1,476〜6,525文字になった。

**対応(2026-09-06に実装)**: `parseAiSearchResponse` で `content[]` を展開し、**1チャンク=1 `ManualChunk`** にした。結合したままだとチャンクごとのスコアが失われ、P2の第1段(top-1スコアによる足切り)が設計どおり実装できないため。展開後の実データ確認:

| 質問 | チャンク数 | スコア | プロンプト文字数 |
|---|---|---|---|
| ろ過フィルターの掃除方法 | 4 | 0.596 / 0.474 / 0.442 / 0.432 | 4,831 |
| 水が逆流するときの対処法 | 4 | 0.617 / 0.451 / 0.414 / 0.413 | 4,029 |
| 有給休暇の申請方法は?(マニュアルに無い) | 0 | — | — |

**関連質問のトップスコア(0.596〜0.617)と、同一ファイル内の関連薄いチャンク(0.41〜0.47)の間に明確な差がある**ため、P2のθ1は0.5前後が出発点になりそう(本キャリブレーションはP4)。

なお展開により、θ1が入るまでは出典が最大10行並ぶ(実測では4行)。これは既知の割り切りで、P2で解消する(`specs/p2-escalation/spec.md` §1-2)。

## 関連する設計判断(抜粋)

- AI Searchのチャンク分割・埋め込みは「スマートデフォルト」のまま開始(env-setup-record §2.2)。精度実測の結果で見直す
- AI Search呼び出し失敗はエスカレーション扱いにフォールバック(誤情報より安全、§6)。ただしエスカレーションフロー自体はP2実装のため、**P1では定型エラーメッセージを返信した上で例外を投げ、SQSリトライ → DLQ隔離に載せる**(計画時に確定)
  - 理由: LINEの`replyToken`は短時間で失効するためリトライ経路では返信できず、ユーザーへの即時フィードバックを優先する。一方でDLQ・CloudWatchアラームによる障害検知の経路は残したい。設計書§3.7の最終形(通知してからDLQへ隔離)と同じ形であり、P2ではreplyをpushに差し替えるだけで済む
- 検索ヒットが0件だった場合は、定型メッセージ(マニュアルに該当する記載が見つからなかった旨)を返す。スコア閾値による足切り・エスカレーションはP2スコープ
- マニュアルのファイルサイズ上限は4MB。超過は索引されずエラーログに残るのみ(§6のリスク — 運用手順はP4)
