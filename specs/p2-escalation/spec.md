# P2 未回答判定+エスカレーション

**元資料**: `docs/design-v5-hybrid.md` §8(P2)、§3.4・§3.5・§3.7
**用語**: 分からない用語は `docs/glossary.md` を参照

## ゴール

未回答質問でメールアドレスを収集し、担当者へメール転送できる。処理失敗時はユーザーへエラーメッセージが届く(F-03, F-04, F-07)。

## 対応する必須要件

| ID | 要件 |
|---|---|
| F-03 | マニュアルで回答不能と判定した場合、回答を保留しメールアドレス入力を促す |
| F-04 | 収集したメールアドレスと質問内容を、固定1名の担当者へメール送信 |
| F-07 | 未回答判定は「検索スコア閾値」+「LLM自己判定」の二段構え |

## スコープ

### 1. 二段階の未回答判定(§3.4)

- **第1段(スコア足切り)**: AI Search top-1スコアが閾値θ1未満なら、LLMを呼ばずエスカレーション。θ1は暫定値で開始し、P4で評価セットによりキャリブレーションする
  - **θ1の出発点(P1の実測、2026-09-06)**: マニュアルに載っている質問のトップスコアは **0.52〜0.62**、同一ファイル内の関連の薄いチャンクは **0.41〜0.47**。マニュアルに無い質問はそもそも**ヒット0件**で返る。この差を踏まえると **0.5前後**が暫定値の候補
  - P1で `parseAiSearchResponse` が `content[]` を1チャンク=1件に展開済みなので、チャンクごとのスコアがそのまま使える(結合されていない)
- **第2段(LLM自己判定)**: 構造化JSON出力を強制する

```json
{
  "answerable": true,
  "answer": "回答本文(answerable が false の場合は空文字)"
}
```

- 出典(`sources`)はJSONに**含めない**。P1で確定したとおり、出典は検索結果からコード側で組み立てる(設計書§3.4)。LLMに出力させると存在しないファイル名を書く余地が残るため
- **安全側への倒し方**: JSONパース失敗・タイムアウト・API障害はすべてエスカレーションに倒す(誤情報より担当者へ繋ぐ方が損害が小さい)

### 1-2. P1レビューでP2に送った申し送り事項

P1の実装で見つかった3点は、いずれもP2の実装で自然に解消される。P2着手時に消化すること。

- **「答えられません」という回答にも出典が付く**: P1の`assembleAnswerReply`はチャンクがあれば無条件に出典を付ける。第2段の`answerable: false`をエスカレーションに倒すことで、この返信自体がなくなる
- **回答に使われていないチャンクのファイルも出典に並ぶ**: 検索ヒット全件を出典化しているため、無関係なファイルも「出典」として提示される。第1段のθ1足切りで低スコアのチャンクを落とすこと
- **リトライが成功しえないのにHaikuを最大3回課金する**: LINEの`replyToken`はSQSの可視性タイムアウト(180秒)より先に失効するため、P1ではリトライしても返信できず必ずDLQ行きになる。上記3(push通知への差し替え)でリトライが意味を持つようになる

### 2. DynamoDB状態機械+エスカレーションフロー(§3.5)

```
[未回答判定成立]
  → NORMAL → WAITING_EMAIL に遷移、質問文を保存
  → 利用目的を明示してメールアドレス入力を依頼
     (「担当者からの返信のみに使用し、返信後は破棄」+「『やめる』で中止可能」)
  → 次のメッセージ:
      ├─ メール形式OK → SESで担当者へ送信 → NORMALへ
      ├─ 「やめる」等 → NORMALへ
      └─ 形式NG → 再入力案内(「別の質問なら『やめる』で戻れる」旨も案内)
                  3回失敗で自動的にNORMALへ戻す(無限ループ防止)
```

- メールアドレスはSES送信後に状態から即座に破棄。DynamoDB TTL(24時間)でも自動消去
- SESはサンドボックスのまま使う(宛先固定1名のため本番アクセス申請不要、§4)

### 3. DLQ到達時のユーザー通知(§3.7)

- worker のcatch-allハンドラで、処理失敗検知時にLINE push APIで「エラーが発生しました。時間をおいて再度お試しください」を送信してからDLQへ隔離
- push送信自体の失敗はログ記録のみ(二重障害まで通知経路を追わない)
- DLQ到達はCloudWatchアラームで検知

### 4. ユーザー単位レート制限(§3.7)

- DynamoDB会話状態レコードに日次カウンタ属性を追加
- 同一ユーザーが**1日20件超**の質問を送った場合、定型メッセージで打ち切る(エスカレーションフローには回さない)
- 背景: 認証なし・不特定多数のため、LLM費用(約¥0.7/質問)の積み上がり対策

## テスト

このフェーズは分岐が多く、ユニットテストの価値が最も高い。状態機械・判定ロジックはすべて外部サービスのモックでテストする。

- [ ] 状態機械の遷移を網羅するユニットテスト:
  - 未回答判定成立 → WAITING_EMAIL へ遷移し質問文が保存される
  - メール形式OK → SES送信(モック)が呼ばれ NORMAL へ戻り、アドレスが状態から消えている
  - 「やめる」 → NORMAL へ戻る
  - 形式NG3回 → 自動的に NORMAL へ戻る(無限ループしない)
- [ ] メールアドレス形式判定のユニットテスト(OK例・NG例)
- [ ] 安全側フォールバックのユニットテスト: LLMのJSONパース失敗・タイムアウト・API障害がすべてエスカレーションに倒れる
- [ ] スコア足切りのユニットテスト: θ1未満はLLMを呼ばずエスカレーション、θ1以上は生成へ進む
- [ ] レート制限のユニットテスト: 20件目は通り、21件目は定型メッセージで打ち切り。日付が変わればリセット

## 完了条件

- [ ] マニュアルにない質問で、メール収集→担当者への転送メールが届く(手動確認)
- [ ] 「やめる」・形式NG3回・TTLの各経路で状態がNORMALへ戻る
- [ ] 処理失敗時(DLQ隔離時)にユーザーへエラーメッセージが届く
- [ ] 1日20件超の質問が定型メッセージで打ち切られる

## スコープ外

- 会話履歴を使ったマルチターン応答・クエリ書き換え(→P3)
- θ1の本キャリブレーション(→P4。P2では暫定値)
