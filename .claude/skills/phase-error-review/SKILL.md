# フェーズ完了時エラーハンドリングレビュー

このフェーズで実装・変更した処理について、「エラーが発生したときに何が起きるか」を一つずつ具体的に追跡し、
CLAUDE.mdの安全原則(**迷ったら安全側 = エスカレーションに倒す**。JSONパース失敗・タイムアウト・API障害はすべて未回答扱い)
に反する挙動がないかを確認する。テストが通っている・lintが通っているだけでは、この観点は担保されない。

## 背景

P0レビューで、webhook/worker Lambdaの一部処理がtry/catchで囲われておらず、例外発生時に
「LINE Webhook再送が既定で無効」という設計上の制約と組み合わさって、イベントが誰にも気づかれず
消失しうる状態になっていた(意図しない挙動)。この種の問題を各フェーズの完了前に機械的に洗い出すためのスキル。

## 手順

### 1. 対象範囲を特定する

`git diff`(このフェーズの作業ブランチとベースブランチの差分、または直近のコミット群)で、
このフェーズで新規追加・変更したファイルを列挙する。特に以下を含む変更を対象にする。

- `apps/*/src/**`(webhook Lambda / worker Lambda のハンドラ・エントリポイント)
- `packages/adapters/src/**`(LINE API・AI Search・DynamoDB・SQS・SES・SSMなど外部サービスへのアクセス)
- `packages/domain/src/**`(状態機械・判定ロジックなど、エラー時のフォールバック先を決める部分)

### 2. 外部境界の呼び出し箇所をすべて洗い出す

対象範囲の中から、失敗しうる呼び出し(例外throw・Promise reject・不正な外部入力のパース)を持つ箇所を
すべてリストアップする。例:

- 外部API呼び出し(LINE返信/署名検証、Cloudflare AI Search `/search`、Claude Haiku生成、SES送信)
- AWSリソースアクセス(DynamoDB read/write、SQS enqueue、SSM Parameter Store取得)
- 外部入力のパース(Webhookボディ、SQSメッセージbody、LLMのJSON出力)

### 3. 箇所ごとに「エラー発生時に何が起きるか」を追跡する

洗い出した各箇所について、次を具体的に確認する。空欄推測ではなく、実際にコードを読んで追跡すること。

- **キャッチされているか**: try/catchで囲われているか、呼び出し元のどこかで最終的に捕捉されるか。
- **キャッチされていない場合**: 例外はどこまで伝播するか。Lambdaハンドラ全体が失敗した場合、
  - webhook Lambda(Function URL)→ LINEプラットフォームに5xxが返る。**LINE Webhook再送は無効**なので、
    このイベントは二度と処理されない(サイレントなイベント消失)。これは許容できるか、それとも
    catchしてログを残す/後続手段(DLQ・アラート等)につなぐべきか。
  - worker Lambda(SQSトリガー)→ バッチ内の1メッセージの例外で、バッチ全体が再試行されないか。
    再試行された場合、既に処理済みの他メッセージ(例: 既にLINE返信済みのもの)が重複処理されないか。
    最終的にDLQに到達した場合、ユーザーへの通知やエスカレーション導線につながっているか(P2以降)。
- **キャッチされている場合**: catchした後の挙動は「安全側」か。
  - ただログを吐いて握りつぶし、処理が正常終了したかのように振る舞っていないか(サイレント失敗)。
  - ユーザーに対して、成功したかのような返信(例: 空の返信、意味不明な返信)をしていないか。
  - JSONパース失敗・タイムアウト・API障害を「未回答」として扱い、エスカレーション経路
    (P2以降)に正しく流しているか。まだエスカレーション経路がないフェーズでは、
    最低限「エラーとして認識できる形」(ログ・メトリクス)に落ちているか。
  - F-01(マニュアルのみを根拠に回答する)に関わる処理では、検索/取得に失敗したときに
    LLMが根拠なく回答(幻覚)する経路に入り込んでいないか。

### 4. 結果をまとめる

チェックした箇所を一覧にして、それぞれ「問題なし」「要修正」を判定する。「要修正」がある場合は、
spec.mdの完了条件にチェックを入れる前に修正する(このスキルはレビューのみを行い、勝手に修正しない。
修正するかどうか・どう直すかはユーザーに確認する)。

レビュー結果は、そのフェーズの `specs/PROGRESS.md` の該当行のメモに一言残す
(例: 「エラーハンドリングレビュー実施済み・問題なし」「◯◯を修正」)。

## 注意

- このスキルは静的なコード追跡によるレビューであり、実行時の網羅的な検証ではない。
  P2以降で評価セットが整備された後は、意図的にAPIエラーを注入した結合テスト・手動確認と併用する。
- 「一見catchされているが、catch節が空、またはconsole.logのみで再スローも安全側フォールバックもしていない」
  パターンを特に重点的に探すこと(見た目上は例外が発生しないように見えてしまうため見逃しやすい)。
