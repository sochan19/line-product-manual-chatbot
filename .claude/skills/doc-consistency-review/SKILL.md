# ドキュメント整合性・整理レビュー

コードの改修やレビューでドキュメントを書き換えると、内容は最新になる一方で、
**ドキュメント群としての整合性が崩れる / 同じ事実が複数ファイルにコピーされる / 1ファイルが肥大化する /
そのファイルの役割から外れた記述が混ざる**ことがある。これらは毎セッションのコンテキスト消費を静かに増やす。
このスキルは、書き換えの直後にドキュメント群を1度俯瞰し、**contextを増やさない形に整理する**ためのもの。

契約は `docs/_docmap.json`(各ドキュメントの役割・所有トピック=SSoT・上限行数)。
機械的に判定できる範囲(サイズ・リンク切れ・見出し重複)は `scripts/check-docs.mjs` が担当し、
このスキルは**人間/AIの判断が要る整合性・重複・役割適合**に集中する。

## いつ実行するか

- CLAUDE.mdルール2で、仕様変更を `docs/design-v5-hybrid.md` と該当specに反映した直後
- フェーズ完了前(`specs/*/spec.md` の完了条件チェック前 / `specs/PROGRESS.md` を「完了」にする前)。
  `phase-error-review` と同じタイミングで、そのあとに実行する
- `docs/**` を変更するPRを出す前

## 手順

### 1. 対象範囲を特定し、機械チェックを先に通す

- `git diff`(このフェーズの作業ブランチとベースブランチの差分、または直近のコミット群)で、
  今回追加・変更したドキュメント(`*.md`)を列挙する。
- `pnpm docs:check`(= `node scripts/check-docs.mjs`)を実行し、**ERROR は全て解消**、
  warn は下の観点で対応要否を判断する。ここで「追跡漏れ」が出た場合は、コードより先に
  `docs/_docmap.json` と CLAUDE.md のドキュメントマップへ新ドキュメントを登録する(ルール2)。

### 2. 整合性 — 他ドキュメントと矛盾していないか

今回の書き換えで生まれた記述が、他のドキュメントの記述と食い違っていないかを確認する。特に:

- **数値・仕様・命名**: タイムアウト値・スコア閾値・エンドポイントのパス・SSMパラメータ名・フォルダ名など。
  例: worker Lambdaのタイムアウトを変えたら、`design-v5-hybrid.md` §3・該当spec・`env-setup-record.md`・
  `PROGRESS.md` のメモの間で値がそろっているか。
- **食い違いがあれば `docs/design-v5-hybrid.md` を正**とし、他方を合わせる(ルール2)。
  設計書自体が古い場合は、設計書を先に直してからspec/記録を合わせる。

### 3. 重複 — 同じ事実が複数ファイルに実体コピーされていないか

- `docs/_docmap.json` の `owns`(所有トピック)に照らし、**所有ドキュメント以外に同じ内容の本体が
  置かれていないか**を確認する。`check-docs.mjs` の「見出し重複」「SSoT越境」warn を起点にする。
- 所有ドキュメント以外は「1〜2行の要約 + 所有ドキュメントへの相対リンク」に置き換える。
  spec は設計書の抜粋を持ってよいが、**抜粋は最小限にし、正は設計書**であることを明記する
  (既存specの「関連する設計判断(抜粋)」の書き方に合わせる)。
- 調査ログ・実測結果が `PROGRESS.md` のメモ欄で長くなっている場合は、本体を該当specへ移し、
  `PROGRESS.md` には結論一言だけ残す。

### 4. 肥大化 — 1ファイルが上限に近づいていないか

- `check-docs.mjs` の「肥大化」ERROR /「肥大化の予兆」warn に対応する。
- 減らし方の優先順位:
  1. **役割の違う記述を正しいドキュメントへ移す**(手順5と重なる)
  2. **陳腐化した節を削る**(実装済みで確定した「要判断」「積み残し」、解決済みの暫定記述)
  3. **読み捨て部分を圧縮する**。特に `design-v5-hybrid.md` 冒頭の「vX.Y での主な変更点」は
     肥大しやすい。直近1〜2版のみ残し、古い版の変更点は削るか末尾へ集約する
- 上限そのものを上げるのは、そのドキュメントの役割上その分量が本質的に必要なときだけ。
  その場合は `docs/_docmap.json` の `maxLines` を先に更新し、理由をコミットメッセージに書く。

### 5. 役割適合 — そのドキュメントに沿った内容か

- 変更した各ドキュメントについて、`docs/_docmap.json` の `purpose` と `notHere` に照らし、
  **はみ出した記述がないか**を確認する。例:
  - 設計書に、作成済みリソースのIDやトークンの置き場所が書かれている → `env-setup-record.md` へ
  - specに、設計の背景説明が長々と書かれている → 設計書へ寄せ、specは抜粋+リンクに
  - `PROGRESS.md` に要件や設計判断の本文がある → 該当specか設計書へ
- はみ出しは正しいドキュメントへ移動し、元の場所にはリンクだけ残す(必要なら)。

### 6. 結果をまとめる

指摘を表にする(例: `ドキュメント / 指摘の種類(整合性・重複・肥大化・役割) / 対応案(移動先・削除・要約+リンク)`)。

- このスキルは**レビューのみ**。修正するかどうか・どう直すかは**ユーザーに確認**してから行う
  (`phase-error-review` と同じ契約)。
- レビュー実施の事実を、そのフェーズの `specs/PROGRESS.md` 該当行のメモに一言残す
  (例: 「ドキュメント整合性レビュー実施済み・問題なし」「設計書§5をenv-setup-recordへ移動」)。

## 注意

- **目的はコンテキスト消費の削減**。「念のため両方に書く」「読み手のために再掲する」といった
  冗長さを増やす方向の指摘はしない。原則は **1事実 = 1箇所 + リンク**。
- `docs/_docmap.json` は契約なので、新ドキュメント追加・役割変更・上限変更のときは
  **コードより先に** `_docmap.json` と CLAUDE.md のドキュメントマップを直し、両者の整合を取る。
- 機械的に判定できる観点(サイズ・リンク・見出し重複・追跡漏れ)は増やすなら
  `scripts/check-docs.mjs` 側に寄せ、このスキルは判断が要る観点に絞り続ける。
