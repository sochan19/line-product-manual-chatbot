# コードコメント・並び順レビュー

このリポジトリのテストは「動くことの確認」だけでなく「仕様書」としても読まれる。読者はAWS/Terraform初心者を
前提としている(CLAUDE.md 開発ルール7)ため、テスト名の英語だけでは何を確かめているのか伝わらない。
また、テストの並びがテスト対象コードの処理順とバラバラだと、コードとテストを行き来しながら読めない。

このスキルは、追加・変更したコードが次の3つの規約を満たしているかを機械的に確認する。

## 規約

### 規約1: テストケースの上に概要コメントを書く

すべての `it(...)` の直上に、そのテストが**何を確かめているか**を日本語1行で書く。
英語のテスト名をそのまま和訳するのではなく、読者が「なぜこの確認が要るのか」を掴める書き方にする。

```ts
// 署名ヘッダーが無いリクエストは、検証にかける前に弾く(P0の入口ガード)
it('rejects a request with a missing signature header', () => {
```

「なぜこのテストを残すか」の背景コメント(実際に踏んだ不具合の回帰テストなど)が既にある場合は消さず、
概要コメントと併記する。

### 規約2: テストは対象コードの分岐実行順に並べる

同じファイル内の `it(...)` は、**テスト対象のコードが実行される順**に上から並べる。判断基準は次のとおり。

1. ガード節・早期return(入力検証、失敗時の即時リターン)を先頭に置く
2. 正常系は、対象関数の処理が進む順に並べる
3. 途中の分岐で発生する異常系は、その分岐が起きる位置に置く
4. 関数の最後に実行される処理(最終的な副作用・戻り値の組み立て)を末尾に置く

結果として正常系がファイル末尾に来ることがある(例: `workerHandler.test.ts` の「回答+出典を返信する」)。
それは対象コードで最後に実行される処理だからであり、規約どおりの正しい並びである。
テストの中身は変えず、順序だけを入れ替えること。

### 規約3: 関数・メソッドの上に用途コメントを書く

実装ファイル・テストファイルを問わず、すべての関数の直上に**何のための関数か**を日本語で書く。
対象は export された関数だけでなく、ファイル内部のプライベート関数、テスト内のヘルパー関数
(`buildEvent()` / `createDeps()` など)も含む。

コードを日本語に置き換えただけの説明(「chunksをループしてsourcesにpushする」)は書かない。
「何のため」「なぜそうするか」を書く(CLAUDE.md 開発ルール6)。

```ts
/** テストごとに差し替えたい依存だけを上書きして、worker Lambdaの依存一式を作る */
function createDeps(overrides: { ... }) {
```

## 手順

### 1. 対象範囲を特定する

`git diff`(作業ブランチとベースブランチの差分、または直近のコミット群)で、追加・変更された
`*.ts` / `*.test.ts` を列挙する。

### 2. テストファイルを確認する

各テストファイルについて:

- `describe` ブロックの直上に、対象が何をするものかの1行コメントがあるか
- すべての `it(...)` に概要コメント(規約1)があるか
- すべてのヘルパー関数に用途コメント(規約3)があるか
- **テスト対象のファイルを実際に読み**、`it` の並びが分岐実行順(規約2)と一致しているか。
  一致しない場合は、正しい順序を具体的に示す(「Aを3番目からBの前へ」のように)

### 3. 実装ファイルを確認する

各実装ファイルについて、export の有無にかかわらず関数ごとに用途コメント(規約3)があるかを確認する。
定数(`searchTimeoutMs` など)にも既存コードと同じくコメントが付いているかを見る。

### 4. 結果をまとめる

ファイルごとに「問題なし」「要修正」を判定し、要修正は箇所と直し方を一覧にする。
このスキルはレビューのみを行い、勝手に修正しない。修正するかどうか・どう直すかはユーザーに確認する。

修正後は `pnpm test` を実行し、並べ替えでテスト結果(件数・成否)が変わっていないことを確認する。

## 注意

- 規約の対象は**関数単位とテストケース単位**に限る。全行にコメントを付けるのはCLAUDE.md 開発ルール6
  (「全行ではなく重要な箇所のみ」)に反するので、行単位のコメントを機械的に増やさせないこと。
- 並べ替えでテストの中身(アサーション・モックの設定)を変えてはいけない。差分が順序の移動だけに
  なっているかを `git diff` で確認する。
