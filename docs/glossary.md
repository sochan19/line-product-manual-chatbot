# 用語集(初心者向け解説)

CLAUDE.md・specs で使っている専門用語の解説。「AWSもTerraformも初めて」の前提で書いています。

## 設計・開発手法

| 用語 | 解説 |
|---|---|
| SDD(Spec-Driven Development / スペック駆動開発) | 「先に仕様書(spec)を書き、それに沿って実装する」進め方。仕様と実装がずれたら仕様書を先に直す。このリポジトリの `specs/` がその仕様書 |
| ポート&アダプタ(ports-and-adapters) | アプリの設計パターンの1つ。中心に「業務ルールそのもの」(ドメイン層。例: 未回答判定のロジック)を置き、外部サービス(AWS・LINE・Cloudflare)とは直接つながない。間に**ポート**(「検索できること」のような約束事 = TypeScriptのinterface)と**アダプタ**(その約束を実際にAI Search等で実現する実装)を挟む。利点は2つ: ①外部サービスを乗り換えてもアダプタの差し替えだけで済む(実際、本プロジェクトは検索をCloudflareに切り替えた際これで安く済んだ)、②テスト時にアダプタを偽物(モック)に差し替えれば、実際のAWSやAPIなしで業務ルールをテストできる |
| モノレポ | アプリのコード(`src/`)とインフラのコード(`infra/`)を別リポジトリに分けず、1つのリポジトリにまとめて管理する方式。関連する変更が1コミットで完結する |
| ユニットテスト | 関数やクラス単位の小さな自動テスト。「この入力ならこの出力になるはず」をコードで書き、コマンド一発で全部検証できる |
| モック | テスト用の「偽物の部品」。例: 本物のAI Searchを呼ぶ代わりに「必ずスコア0.9でこのチャンクを返す偽物」を使い、外部APIなしでロジックだけを検証する |
| CI/CD | コードをGitHubにpushするたびに、テスト実行(CI)やデプロイ(CD)を自動で走らせる仕組み。本プロジェクトではGitHub Actionsを使う |
| lint | 「使っていない変数がある」等、コードの問題を自動チェックするツール |
| ADR(Architecture Decision Record) | 「なぜその技術を選んだか」の判断記録。本プロジェクトでは設計書§2の案A〜F比較がその元ネタ |
| 評価セット | ボットの精度を測るための質問リスト(答えられるはずの質問30問+答えられないはずの質問10問)。人間の感覚でなく数字で精度を語るために使う |
| キャリブレーション | 閾値などの設定値を、机上で決め打ちせず実データ(評価セット)で試して調整すること |

## AWS

| 用語 | 解説 |
|---|---|
| Lambda(ラムダ) | サーバーを自分で用意せずにコードを実行できるAWSのサービス。リクエストが来た時だけ動き、動いた分だけ課金(本プロジェクトの規模なら無料枠内) |
| Function URL | Lambdaに直接HTTPSのURL(`https://xxx.lambda-url...`)を1本生やす機能。これをLINEのWebhook URLとして登録する |
| SQS / キュー | メッセージの「待ち行列」。webhook Lambdaが受けた質問を一旦ここに入れ、worker Lambdaが順に取り出して処理する。処理に失敗してもメッセージは消えず、自動でやり直される |
| DLQ(デッドレターキュー) | 何度やり直しても失敗したメッセージの隔離場所。「失敗した質問」を後から調査できる |
| DynamoDB | AWSのデータベース(キーと値を保存するタイプ)。会話の状態や履歴を保存する |
| TTL(Time To Live) | データに有効期限を付け、期限が来たら自動削除するDynamoDBの機能。メールアドレス等を確実に消すために使う |
| 条件付き書き込み | 「まだ存在しない場合だけ書き込む」というDynamoDBの機能。同じイベントIDが既にあれば処理済みと分かる(→冪等性) |
| SES | AWSのメール送信サービス。「サンドボックス」は検証済みアドレスにしか送れないお試しモードのことで、宛先が担当者1名固定の本プロジェクトではそのままで足りる |
| SSM Parameter Store | APIキーなどの秘密情報の保管庫。コードに直書きせずここから読む。SecureString = 暗号化して保存する形式 |
| EventBridge Scheduled Rule | 「14日ごとに実行」のような定期実行タイマー。指定した間隔でLambdaを起動できる |
| CloudWatch | AWSのログ・監視サービス。「DLQにメッセージが入ったら通知」のような**アラーム**を設定できる |
| OIDC連携 | GitHub ActionsがAWSにデプロイする際の認証方式。長期パスワード(アクセスキー)をGitHubに保存する代わりに、実行のたびに短時間だけ有効な証明書で認証する。キー漏洩リスクがなくなる |

## Terraform(IaC)

| 用語 | 解説 |
|---|---|
| IaC(Infrastructure as Code) | インフラ(Lambda、SQS等)を画面ポチポチでなくコードで定義する考え方。何を作ったかがコードに残り、作り直しも再現できる |
| Terraform | IaCの代表的ツール。`.tf` ファイルに「あるべき構成」を書き、`terraform apply` で実際のクラウドをその状態にする |
| プロバイダ | TerraformがAWSやCloudflareを操作するためのプラグイン。本プロジェクトは2プロバイダ(AWS + Cloudflare)構成 |
| state(ステート) | Terraformが「今どのリソースを作ってあるか」を記録するファイル。これが壊れると実態と管理がずれるので大事に扱う |
| S3バックエンド | stateファイルをローカルでなくS3(AWSのファイル置き場)に保存する設定。PCが変わってもstateを共有できる |
| stateロック | 2つのterraform実行が同時にstateを書き換えて壊すのを防ぐ排他制御。Terraform 1.10以降はS3だけで実現できる(それ以前はDynamoDBテーブルが必要だった) |
| import | 手動(ダッシュボード)で作ってしまった既存リソースを、後からTerraformの管理下に取り込む操作 |

## LINE・Webhook まわり

| 用語 | 解説 |
|---|---|
| Webhook | 「イベントが起きたら、あちらからこちらのURLへHTTPで通知してくる」仕組み。ユーザーがボットにメッセージを送ると、LINEが我々のFunction URLを呼び出してくる |
| 署名検証 | 届いたリクエストが本当にLINEからのものか(なりすましでないか)を確認する処理。LINEと共有している秘密(Channel Secret)で計算した署名を照合する |
| 冪等性(べきとうせい) | 同じ処理をうっかり2回実行しても、結果が1回のときと同じになる性質。同じ質問に2回返信しないよう、イベントIDをDynamoDBに記録して2回目をスキップする |
| reply / push | LINEの2つの返信方式。**reply** = メッセージ受信時にもらえるトークンを使ってすぐ返す(無料・時間制限あり)。**push** = こちらの好きなタイミングで送る(エラー通知等に使用) |
| レート制限 | 1ユーザーの利用回数に上限を設けること(本プロジェクトは1日20質問)。悪意ある大量送信でLLM費用が膨らむのを防ぐ |

## RAG・Cloudflare

| 用語 | 解説 |
|---|---|
| RAG(Retrieval-Augmented Generation) | 「検索で見つけた文書をLLMに渡し、それだけを根拠に回答させる」方式。LLMの記憶でなくマニュアルに基づいて答えさせるための土台 |
| チャンク | 検索しやすいようにマニュアルを分割した断片。検索はチャンク単位でヒットする |
| 埋め込み(embedding)/ ベクトル検索 | 文章を数値の並び(ベクトル)に変換し、「意味が近い文章」を探せるようにする技術。キーワード一致でなく意味で検索できる |
| top-1スコア / 閾値θ1(シータワン) | 検索結果の最上位チャンクの類似度スコア。これが閾値θ1未満なら「マニュアルに答えがない」とみなしてエスカレーションする。θ1の値は評価セットで調整する |
| R2 | Cloudflareのファイル置き場(AWSのS3に相当)。マニュアルの.mdを`manuals/`フォルダに置く |
| AI Search | Cloudflareのマネージド(=お任せ)RAGサービス。R2にファイルを置くだけで、チャンク分割→埋め込み→索引化を全自動でやってくれる(.docx等を置いた場合はMarkdownへの変換も行う)。我々はREST APIで検索を呼ぶだけ |
| プロンプト / システムプロンプト | LLMに渡す指示文。**システムプロンプト**は「マニュアルの抜粋だけを根拠に答える」のような役割・制約の指示、ユーザープロンプトは質問文と検索でヒットしたチャンクを載せる部分。本プロジェクトではこの組み立て自体が業務ルール(F-01)なのでドメイン層に置く |
| トークン / max_tokens | LLMが文章を扱う単位(日本語なら1文字〜数文字で1トークン程度)。課金もこの単位。`max_tokens`は1回の回答で生成できる上限で、これを超えると文章が途中で切れる |
| レイテンシ | 呼び出してから応答が返るまでの所要時間。P1ではAI Search呼び出しのレイテンシを実測して記録する |
| エスカレーション | ボットで答えられない質問を、人間の担当者へ引き継ぐこと(メールアドレスを聞いてSESでメール転送) |
| 状態機械(ステートマシン) | 会話の状態(通常モード / メールアドレス待ちモード)と、その切り替わりルールを明文化したもの。「今どのモードか」で同じ入力への反応を変える |
