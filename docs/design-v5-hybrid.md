## 1. プロジェクトの背景・目的・意図

### 1.1 背景

開発者(以下「担当者」)は、業務で使用するWordマニュアル群への問い合わせ対応を自動化したいという実務上のニーズを持っている。同時に、担当者は転職活動を控えており、本プロジェクトを**技術力を示すポートフォリオ**としても活用したいという意図がある。

この2つの目的は必ずしも一致しない。実務上は「最速・最安で動くもの」が正義だが、ポートフォリオとしては「設計判断の深さ・技術的説明力」が評価される。**本設計書の全体を通じて、この2つの目的のバランスをどう取ったかを明示することを重視している。**

### 1.2 やりたいこと(要件の要約)

Wordファイルのマニュアルを**唯一の情報源**として、LINEで届いた質問に自動で回答するボットを作る。マニュアルに答えがない質問は、ユーザーからメールアドレスを聞き取り、固定1名の担当者へメール転送する。担当者はそのアドレス宛に直接返信する(システム側での自動返信は行わない)。

### 1.3 必須要件

| ID | 要件 |
|---|---|
| F-01 | 回答の根拠はマニュアルのみ。LLMの学習知識やWeb検索結果を使った回答を禁止する |
| F-02 | 回答時に出典(ファイル名を必須、見出しが取得できる場合はあわせて提示)を提示する |
| F-03 | マニュアルで回答不能と判定した場合、回答を保留しメールアドレス入力を促す |
| F-04 | 収集したメールアドレスと質問内容を、固定1名の担当者へメール送信する |
| F-05 | 同一ユーザーの直近会話文脈を踏まえたマルチターン応答 |
| F-06 | マニュアルファイル更新時、人手を介さず検索インデックスへ自動反映 |
| F-07 | 未回答判定は「検索スコアの閾値」と「LLM自身による回答可能性の自己判定」の二段構えとする |

### 1.4 制約・前提

- マニュアルは複数の .docx。表・画像等の複雑レイアウトは含まない。
- 機密情報・個人情報を含まないため、外部LLM APIへの送信に制約なし。
- 日本語のみ対応。利用者は不特定多数(LINE友だち登録のみ、認証なし)。
- 想定トラフィック: 月間利用者10人程度、月間50質問程度(小規模)。
- **予算: 月額2,000円以内**(サーバーレス+従量課金APIを基本方針とするが、最終判断は設計側に委ねる)。
- AWSアカウントは保有済み。**IaCはTerraformを使用する**(開発者の市場性・既存スキルとの整合を優先)。
- 開発方針: TypeScript、CI/CD、IaC、テスト等、モダンな開発プラクティスを取り入れる。
- 開発者は実質1名。開発体制・納期の制約は特になし。

### 1.5 設計における意図:ITコンサルタント的判断基準の明示

本プロジェクトの設計プロセスにおいて、開発者から以下の明確な方針が示された(この方針が、本設計書全体を貫く判断基準である):

> 「AIコンサルタントとして、コストと利便性を天秤にかけて実装したい。無理に勉強のために高いハードルを越える必要はない。課題解決に適切なツールを使い、最低限にコストをかけることがコンサルに必要な条件である。」

この方針に基づき、設計プロセスでは以下を徹底した:

1. **技術的に高度な実装と、実務上最も合理的な選択は、必ずしも一致しないという前提に立つ。**
2. **既製品・マネージドサービスで要件を満たせるなら、自作しない。** ただし「既製品で本当に要件を満たせるか」は具体的な制約(API有無、料金体系、機能範囲)を調べた上で判断する。
3. **自作が必要な部分についても、実装量・運用複雑性・コストの3点を測定可能な形で比較する。**
4. **最終的な判断だけでなく、比較検討のプロセス自体を文書化する。** これは「なぜこの案を選ばなかったか」を説明できることが、「なぜこの案を選んだか」を説明することと同等以上に、設計能力の証明になるという考えに基づく。

以降の章は、この基準に沿って行った比較検討のプロセスと、最終的に採用した設計を記載する。

## 2. 検討した選択肢とプロセス(コンサル視点での比較検討)

要件を満たす方法として、以下の5案を検討した。検討順に記載する。

### 2.1 案A: LINE公式アカウント「AIチャットボット(β)」

LINE公式アカウントには、事前登録したQ&Aリストから生成AIが最適な回答を選ぶ機能がある。

**不採用の理由**:
- Wordファイルを直接情報源にできず、Q&A形式への手動変換が必要(F-01, F-06を満たさない)
- マニュアル更新の自動反映ができない(F-06を満たさない)
- エスカレーションフロー(F-03, F-04)を組めない
- 稼働には月額3,000円の「チャットProオプション」契約が必要で、予算(月2,000円)を単体で超過する
- コードを一切書かないため、ポートフォリオとしての技術的深みがない

**判定**: 要件を満たさないため、比較対象から除外。

### 2.2 案B: Google NotebookLM

指定した文書のみを情報源とする点で本要件と親和性が高いと考え検討した。

**不採用の理由**:
- 個人向け(無料/Pro)プランには外部連携用のAPIが存在しない。ブラウザでの人間の操作が前提であり、LINEから自動的に呼び出すことができない
- API連携が可能なのは NotebookLM Enterprise(Google Cloud基盤の法人向け)のみで、価格帯・契約形態が本件の想定から外れる

**判定**: 個人プランでは技術的に要件を満たせないため、比較対象から除外。

### 2.3 案C: ノーコードRAGプラットフォーム(Dify等)

LINE公式連携が標準機能として用意されており、ノーコードでRAGパイプライン(ファイルアップロード→チャンク分割→検索→生成)が完結するプラットフォーム。

**評価**:
- 長所: 構築期間が数時間程度、無料枠から開始可能、LINE連携が標準搭載
- 短所: マニュアル自動反映(F-06)は完全ノーコードでは閉じず、結局S3等との連携コードが必要になる。未回答時の細かい会話制御(状態機械)の自由度がコードで書く場合より低い。マニュアルの内容が外部クラウド(プラットフォーム提供元)を経由する。ポートフォリオとして「導入した経験」にはなるが「作った経験」にはなりにくい

**判定**: 実務上は依然として有力な選択肢だが、担当者の「ポートフォリオとしての技術的深みも重視したい」という意向を踏まえ、今回は不採用。ただし比較対象として文書に残す価値があると判断し、本設計書にも記録する。

### 2.4 案D: AWSフルスクラッチ(自作RAG)

Wordファイルの解析、チャンク分割、埋め込み生成、ベクトル検索、未回答判定を全て自前でLambda上に実装する案。

**評価**:
- 長所: 月額コストが最も低い(約¥50〜100)。RAGアーキテクチャ全体を実装した経験がポートフォリオとして最も雄弁。ベンダーロックインが最も少ない
- 短所: 実装量が最大。特にマニュアルの索引化パイプライン(docx解析・チャンク分割・埋め込みAPI呼び出し・索引書き出し)の自作コストが高い。完成までの時間リスクが最大

**判定**: コストは最良だが、実装量の観点で「利便性」とのバランスに課題があると判断。

### 2.5 案E: Cloudflare AI Search 全面移行

Cloudflareが提供するマネージドRAG基盤(AI Search、旧AutoRAG)を用い、R2にファイルを置くだけで索引化が完結する構成。Webhook受信・非同期処理もCloudflare Workers/Queuesに統一する案。

**評価**:
- 長所: マニュアル索引化の自作コードが完全にゼロになる(案Dの最大の弱点を解消)
- 短所: **月額コストが案Dより高くなる**(約¥810)。原因はCloudflare Queuesの利用にWorkers Paidプラン($5/月固定)が必須なため。この固定費が、AI Search自体は無料である恩恵を上回ってしまう構造的な問題があった

**判定**: 実装量は最小だが、コスト面で案Dに劣後する。「良いとこ取りができないか」を追加検討した。

### 2.6 案F: AWS + Cloudflare AI Search ハイブリッド(★最終採用)

案Dと案Eの長所のみを組み合わせられないかを検証した結果、技術的に成立することを確認した。

**成立の鍵**: Cloudflare AI Search には、Cloudflare Workersを経由しない標準REST API(`https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/ai-search/instances/{NAME}/search`)が存在する。これは通常のHTTPSエンドポイントであり、**AWS Lambdaから直接呼び出せる。**

これにより、以下の役割分担が可能になる:

| 担当 | 内容 |
|---|---|
| Cloudflare(AI Search + R2のみ契約) | マニュアルの索引化・検索(実装コードほぼゼロ) |
| AWS(Lambda/SQS/DynamoDB/SES) | Webhook受信・非同期処理・会話状態・エスカレーション・メール送信 |

Cloudflare WorkersやQueuesは一切使わないため、案Eでコスト増の原因となっていたWorkers Paidプランの固定費が発生しない。

**評価(正直な比較)**:

| | 案D(AWS単独) | 案E(Cloudflare単独) | **案F(ハイブリッド)** |
|---|---|---|---|
| 月額コスト | 約¥50〜100 | 約¥810 | **約¥50〜100** |
| マニュアル索引化の実装量 | 多い(自作) | ゼロ | **ゼロ** |
| 管理するクラウド数 | 1 | 1 | **2** |
| 外部LLM/埋め込みベンダー数 | 3社(Anthropic/OpenAI/AWS) | 2社(Anthropic/Cloudflare) | 2社(Anthropic/Cloudflare) |

**判定**: コスト・実装量の両面で最も優れるが、**管理するクラウドが2つになるという新たな複雑性を負う。** このトレードオフが許容範囲かどうかを§7で正直に評価した上で、最終案として採用した。

### 3.3 なぜ非同期処理(SQS)が必須か

**訂正(v5.0)**: v4.0では「LINEはWebhook応答が遅延すると同一イベントを再送するため、非同期処理が構造的に必須」としていたが、これは不正確だった。LINEのWebhook再送は**既定で無効**であり、有効化するにはLINE Developersコンソールでの明示的な設定が必要である。本プロジェクトでは再送を有効化する運用は採らない(理由は後述)ため、「再送への対処」を非同期化の主根拠にはしない。

非同期化(SQS)が必要な本当の理由は以下の2点である:

1. **Lambda処理失敗時のイベント消失防止**: webhook Lambda が同期的にRAG処理(検索+LLM生成、通常3〜8秒)まで行い、その途中でLambdaがタイムアウト・クラッシュした場合、再送が無効な設定下ではそのメッセージは**二度と処理されず消失する**。SQSを挟むことで、worker Lambda側の処理失敗はSQSの可視性タイムアウト経由で自動的にリトライされ、最終的な失敗のみDLQへ隔離される。
2. **LINEプラットフォーム側のタイムアウト回避**: LINEはWebhook応答を一定時間待つが、RAG処理を同期実行すると応答が遅延し、LINE側のエラー統計に記録されたりリクエストがタイムアウト扱いになったりする可能性がある。即時200応答によりこれを避ける。

対策として3層を実装する:

1. **即時200応答**: webhook Lambda は署名検証とキュー投入のみを行い、100ms以内に200を返す
2. **冪等性の確保**: `webhookEventId` を DynamoDB に条件付き書き込みし、既存であれば処理をスキップする。これはLINE側の再送(将来有効化する場合や、まれに発生しうる重複配信)への保険であり、SQS自体のat-least-once配信によるworker側の重複実行にも同時に効く
3. **DLQ**: リトライしても失敗したメッセージはDLQへ隔離し、CloudWatchアラームで検知する

**Webhook再送設定について**: 本設計では再送を有効化しない方針とする。理由は、(a) 冪等化とDLQによってLambda起因のイベント消失は既に防げているため再送によるメリットが限定的であること、(b) 再送を有効化すると「同一イベントに対しworkerが複数回起動しうる」経路が増え、冪等化ロジックのテスト対象が広がることの2点による。将来的にLINE側の配信失敗が実運用で観測された場合は、再送有効化を追加の保険として検討する。

### 3.4a マルチターン時のクエリ書き換え(query condensation)

F-05(マルチターン対応)とF-07(二段階の未回答判定)は、そのまま組み合わせると相互に干渉する。ユーザーの発話が「それはどこで設定できますか?」のような文脈依存文の場合、その文字列をそのままAI Searchに渡すと、埋め込み検索が関連チャンクを引けずtop-1スコアが閾値θ1を下回り、**本来は回答可能な質問が誤ってエスカレーション判定される。**

これを防ぐため、検索呼び出しの直前に以下のステップを挿入する:

1. 直近の会話履歴(最大6ターン)と最新の発話をHaikuに渡し、「会話履歴を踏まえた、それ単体で意味が通る検索用クエリ」に書き換えさせる(例:「それはどこで設定できますか?」→「〇〇機能の設定画面はどこにあるか」)
2. 書き換え後のクエリをAI Searchの`/search`に渡す
3. 元の発話(書き換え前)は、最終的な回答生成プロンプトの「ユーザーの質問」としてはそのまま使う(書き換えは検索用途に限定し、回答文言が不自然にならないようにする)

このステップはHaiku呼び出しを1回追加するのみで、月間コスト影響は数円程度に収まる(§5参照)。なお、AI Searchが提供する`rewrite_query`オプションは単発クエリの検索最適化(表記揺れの吸収等)であり会話履歴を参照しないため、この用途の代替にはならない。

**P3完了条件の強化**: §8のP3完了条件は「文脈依存質問が通る」だけでなく、「文脈依存質問を含む評価セットで誤エスカレーション(本来回答可能な質問が未回答判定される)が発生しないこと」を含めるものとする。

### 3.4 未回答判定ロジック(二段構え)

「マニュアルのみを根拠とする」制約(F-01)は、**アーキテクチャとプロンプトの両面**で担保する。

**第0段(アーキテクチャによる物理的制約)**: LLMにはツール(Web検索等)を一切与えない。プロンプトに含めるのはAI Searchでヒットしたチャンクのみとし、LLMが到達可能な情報を物理的に検索結果の範囲に限定する。

**第1段(検索スコアによる足切り)**: AI Searchから返るtop-1スコアが閾値θ1未満の場合、LLMを呼び出さずエスカレーションする。閾値は固定値を信じず、評価セット(想定質問30問+回答不能質問10問)でキャリブレーションする。

**第2段(LLM自身による回答可能性判定)**: 自由文で「わかりません」と言わせて文字列マッチする設計は脆いため、構造化JSON出力を強制する。

```
出力形式(厳守):
{
  "answerable": true | false,
  "answer": "回答本文(answerable が false の場合は空文字)"
}
```

出典(`sources`)はこのJSONに含めない。理由は次項に記す。

安全側への倒し方として、JSONパース失敗・タイムアウト・API障害はすべて「エスカレーション」に倒す。誤情報を返すより、担当者へ繋ぐ方が業務上の損害が小さいという判断による。

**P1時点での例外**: エスカレーションフローはP2で実装するため、P1では検索・生成の失敗時に定型メッセージを返信した上で例外を投げ、SQSのリトライ → DLQ隔離に載せる。ユーザーへの通知手段は、P1ではreply(受信時のトークンでの返信)、P2で§3.7のpush(ユーザーID宛の送信)に差し替える。

**出典表示(F-02)の生成方式とフォールバック仕様**: 出典はLLMに出力させず、**検索結果(ファイル名+チャンク本文)からコード側で組み立てる**。LLMに出力させると存在しないファイル名を書く余地が残るのに対し、コード側で組み立てれば検索でヒットしたファイル以外は構造的に出典に現れず、後述のフォールバックも決定的なユニットテストで検証できるためである。

AI Searchの検索結果には、チャンクが由来するファイル名は常に含まれるが、「そのチャンクがどの見出しに属するか」がメタデータとして常に取得できる保証はない(docx→Markdown変換後のチャンク分割の粒度に依存する)。そのため、出典の生成ロジックは以下のフォールバックを持つ:

1. チャンク本文の先頭付近に見出し相当の行(Markdownの`#`〜`###`など)が含まれる場合は、それを抽出して「ファイル名 > 見出し」の形式で提示する
2. 見出しが抽出できない場合は、ファイル名のみを提示する(「ファイル名 > 見出し」ではなく「ファイル名」単体)
3. F-02の受け入れ基準は「出典としてファイル名を必ず提示し、見出しが取得できる場合はあわせて提示する」に修正する

### 3.5 エスカレーションフロー

```
[未回答判定が成立]
  → state: NORMAL → WAITING_EMAIL に遷移、質問文を保存
  → 「マニュアルからはお答えできませんでした。担当者におつなぎするため、
     メールアドレスをご返信ください。いただいたアドレスは担当者からの
     返信のみに使用し、返信後は破棄します。(『やめる』で中止可能)」
  → ユーザーの次のメッセージ
      ├─ メール形式OK → SESで担当者へ送信 → state を NORMAL に戻す
      ├─ 「やめる」等 → state を NORMAL に戻す
      └─ 形式NG → 「メールアドレスの形式でお送りください。別のご質問の場合は
                  『やめる』とお送りいただければ質問を続けられます」と案内し
                  再入力を促す(3回失敗で自動的にNORMALへ戻し無限ループを防止)
```

収集したメールアドレスはSES送信後に状態から即座に破棄し、DynamoDBのTTL(24時間)によっても自動消去される。メッセージ文言に利用目的(担当者からの返信にのみ使用し、返信後に破棄する旨)を明示することで、不特定多数から個人情報を取得する際の説明責任を担保する。また、WAITING_EMAIL中にユーザーが別の質問を送ってきた場合に「やめる」と送れば通常の質問応答に戻れることを案内し、無用な離脱・ユーザーの混乱を防ぐ。

### 3.6 マニュアル自動反映フロー

```
1. 運用者が R2 の manuals/ に .docx をアップロード(または削除)
2. AI Searchが自動的に同期ジョブを実行
     ・docx → Markdown変換(内蔵機能)
     ・チャンク分割(自動)
     ・埋め込み生成(内蔵、Workers AI経由)
     ・ベクトル格納(自動)
3. 数分〜数十分後、検索結果に反映される
```

実装コードはゼロ。AWS単独案(案D)で最も複雑だった自作ingest処理が丸ごと不要になる。

**運用上の注意**: AI Searchは31日間検索リクエストがないと、外部データソース(R2)に対する定期同期ジョブが自動的に一時停止する仕様がある。一時停止中もインスタンス自体は検索可能なままであり(既存の索引に対する検索は継続する)、実害は「マニュアル更新が索引に反映されない期間が発生する」ことに限られる。また検索トラフィックが再開すれば同期ジョブは自動的に再開される。

月10人規模の低頻度利用では、月によっては31日を超える無操作期間が発生しうる。境界値ぎりぎりの月次実行では暦の関係で漏れが起きうるため、AWS EventBridge Scheduled Rule + 軽量Lambdaで**14日ごと**にダミーの検索クエリを送信し、同期停止を確実に防ぐ設計とする。

### 3.7 障害時のユーザー通知と濫用対策

**DLQ到達時のユーザー通知**: v4.0の設計では、worker Lambdaの処理がリトライしても失敗しDLQに隔離された場合、ユーザーには何も返らず無応答のまま放置されていた。問い合わせボットとして無応答は最悪のUXであるため、worker内のcatch-allハンドラで、処理失敗を検知した時点でLINE push APIにより「エラーが発生しました。時間をおいて再度お試しください」を送信する一段を追加する。このpush送信自体が失敗した場合はログに記録した上でDLQへ隔離する(二重障害まで通知経路を追わない)。

**ユーザー単位のレート制限**: 本ボットは認証なしで不特定多数からLINE友だち登録のみで利用可能なため、悪意あるユーザーが短時間に大量の質問を送るとLLM費用が積み上がる経路がある(1質問あたり約¥0.7)。DynamoDBの会話状態レコードに日次カウンタ属性を1つ追加し、「同一ユーザーが1日あたり20件を超える質問を送った場合はエスカレーションフローに回さず定型メッセージで打ち切る」形の簡易レート制限を実装する。追加コストはほぼゼロ(既存のDynamoDB書き込みに1属性追加するのみ)。あわせて、Anthropicコンソール側でのAPI利用上限(spend limit)設定も運用手順として明記する。

| リスク | 影響 | 対策 |
|---|---|---|
| SQSのat-least-once配信によるworker重複実行(まれに発生) | ユーザー体験悪化・費用増 | webhookEventIdの条件付き書き込みで冪等化(§3.3)。なおLINE Webhook再送は既定無効のため、二重回答の主因はSQS側の再配信である |

| DLQ到達時の無応答 | ユーザー体験悪化 | エラー時はpush APIで定型エラーメッセージを送信してから隔離する(§3.7) |

## 7. トレードオフの正直な評価(セルフレビュー)

コンサルタント視点での結論を出す前に、本設計の弱点を隠さず記載する。

### 7.1 デメリット

- **2クラウド運用の複雑さ**: 障害発生時、AWS側かCloudflare側かの切り分けコストが増える。監視ダッシュボードも2箇所になる。
- **クロスクラウド呼び出しの単一障害点**: worker LambdaからAI Searchへの呼び出しが唯一の検索経路になるため、Cloudflare側の障害がボット全体の障害に直結する。ただしエスカレーションへのフォールバックで実害は緩和される。
- **秘密情報・請求の分散**: Cloudflare API Tokenという新しい管理対象が増える。AWS Budgetsだけでは全体のコストを把握できず、Cloudflare側も別途監視が必要。
- **ポートフォリオとして諸刃の剣**: 「なぜ2つのクラウドを使ったのか」を明確に説明できないと、単に複雑にしただけに見えるリスクがある。本設計書の§2(比較検討プロセス)を提示できることが前提の判断である。

### 7.2 それでも採用した理由

- 月10人規模・開発者1名という前提では、2クラウド運用の運用負荷は現実的に小さい。
- 単一障害点のリスクは、「答えられない扱いにフォールバックする」既存の設計方針で吸収できる。
- ポート&アダプタ構成を採用していたため、方針転換のコストが低かった(検索アダプタの差し替えのみで済んだ)。これは初期設計時点でのアーキテクチャ判断が、後の意思決定の自由度を広げた実例である。

### 7.3 コンサルタント視点での自己評価

冒頭(§1.5)で述べた判断基準に照らすと:

| 判断基準 | 自己評価 |
|---|---|
| 技術的高度さと実務合理性を区別したか | ○:自作RAG(案D)を「技術的には優れるが実装量で劣後する」と正しく評価した |
| 既製品で足りるかを先に検討したか | ○:案A・B・Cを先に検討し、要件を満たせない/最適でない理由を明示した上で除外した |
| 実装量・運用複雑性・コストを測定可能な形で比較したか | ○:各案でコスト試算・実装範囲表を作成した |
| 比較検討のプロセス自体を残したか | ○:本章(§2)が該当する |

一方で、以下は限界として認識している:

- コスト試算はいずれも机上の見積もりであり、実測値ではない。P1フェーズでの実測(特にAI Search呼び出しのレイテンシ、§3節参照)による検証が必要。
- 「2クラウド運用の複雑さ」は定性的な評価に留まり、定量化できていない。
